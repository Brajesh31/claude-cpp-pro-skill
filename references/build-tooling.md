# C++ Build Tooling

## Choose a build system

- Use **CMake** for portable, multi-platform libraries and applications.
- Use **Meson** when fast configuration and a compact build definition matter.
- Use **Bazel** when a large monorepo needs hermetic, cacheable builds.
- Use **Ninja** as a fast backend, normally generated by CMake or Meson.
- Use the compiler directly only for small experiments or isolated diagnostics.

## Minimal CMake project

```cmake
cmake_minimum_required(VERSION 3.20)
project(example LANGUAGES CXX)

add_library(core src/core.cpp)
target_include_directories(core PUBLIC include)
target_compile_features(core PUBLIC cxx_std_20)

add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE core)

include(CTest)
if(BUILD_TESTING)
  add_executable(core_tests tests/core_tests.cpp)
  target_link_libraries(core_tests PRIVATE core)
  add_test(NAME core_tests COMMAND core_tests)
endif()
```

Prefer target-scoped properties over global compiler flags. Use `PRIVATE`, `PUBLIC`, and `INTERFACE` deliberately so dependencies do not leak into consumers.

## Build configurations

Keep separate build directories for different toolchains and modes:

```bash
cmake -S . -B build/debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug --parallel
ctest --test-dir build/debug --output-on-failure

cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release --parallel
```

For multi-configuration generators such as Visual Studio, select the configuration at build time with `--config Debug` or `--config Release`.

## Diagnostics and hardening

Useful GCC/Clang flags for development:

```text
-Wall -Wextra -Wpedantic -Wconversion -Wshadow
```

For supported toolchains, use sanitizers in a dedicated test build:

```text
-fsanitize=address,undefined -fno-omit-frame-pointer
```

Enable warnings in CI, but avoid compiler-specific options without checking the compiler first. Do not treat warning suppression as a fix.

## Dependency management

- Prefer a small number of pinned, reviewed dependencies.
- Use CMake FetchContent, package managers, or vendored dependencies consistently.
- Pin versions or commit hashes for reproducible builds.
- Review licenses, release cadence, security advisories, and transitive dependencies.
- Do not download and execute arbitrary build scripts during configuration.

## Release checklist

1. Build from a clean checkout.
2. Run unit and integration tests.
3. Test Debug and Release configurations.
4. Run sanitizers where available.
5. Verify install/export targets if publishing a library.
6. Record compiler, standard-library, and dependency versions.
7. Package symbols and useful build metadata for debugging.
